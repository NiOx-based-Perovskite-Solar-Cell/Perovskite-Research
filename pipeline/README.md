# pipeline — เตรียมข้อมูลจาก Raw Excel ถึง `prepared_v2`

แทนการรัน notebook 3 ตัวตามลำดับด้วยมือ ตรรกะเหมือนเดิมทุกไบต์ (มีคำสั่งพิสูจน์ให้)

```bash
python run_pipeline.py                # รันทั้งเส้น
python run_pipeline.py --stage 3      # รันขั้น 3 ตัวเดียว (ใช้ผลขั้น 2 ที่มีอยู่)
python run_pipeline.py --from 2       # รันขั้น 2 ถึงจบ
python run_pipeline.py --dry-run      # คำนวณอย่างเดียว ไม่เขียนไฟล์
python run_pipeline.py --strict       # ของใหม่ที่กติกาไม่รู้จัก = หยุด (พฤติกรรมเดิมของ notebook)
python run_pipeline.py verify         # พิสูจน์ว่าผลตรงกับ notebook ทุกไบต์
```

## เส้นทางข้อมูล

| 2 | `column_prepare.ipynb` | `processed/normalize/` | `processed/prepared/` + `processed/audit/` |

`run_pipeline.py verify` แตกชุดข้อมูลอ้างอิงจาก git (commit ที่ `processed/` ถูกสร้างจาก
`Raw Data` ชุดเดียวกัน) รัน pipeline ใหม่ แล้วเทียบ CSV **29 ไฟล์แบบไบต์ต่อไบต์**
(ถ้า commit ผลลัพธ์ชุดใหม่แล้ว ให้อัปเดต `VERIFY_REF` ใน `run_pipeline.py` หรือส่ง `--ref`)

### เมื่อเราตั้งใจแก้สิ่งที่ notebook ทำไม่ครบ

pipeline เริ่มแก้บั๊กที่ notebook มี (เช่นหน่วยที่สะกดต่างจนค่าไม่เข้าคอลัมน์) ผลลัพธ์จึง
ต่างจาก notebook โดยตั้งใจ — ประกาศไฟล์พวกนั้นไว้ใน `overrides/known_deviations.csv`
พร้อมเหตุผล แล้ว verify จะรายงานแยกเป็น "ต่างตามที่ประกาศไว้"

**ไฟล์ที่ต่างโดยไม่ได้ประกาศ = ผลลัพธ์เปลี่ยนแบบไม่ได้ตั้งใจ ต้องหาสาเหตุก่อนใช้ต่อ**
ตาข่ายนี้ยังทำงานเหมือนเดิม แค่แยกของที่ตั้งใจออกจากของที่หลุด

## ทำไมไม่ต้องไล่เช็คทีละเคสแล้ว

notebook เดิมใช้ `assert` ทุกด่าน ข้อมูลชุดใหม่ที่มีรูปแบบไม่เคยเจอจะทำให้ตายกลางทาง
แล้วต้องไล่แก้ทีละเคสก่อนรันต่อได้ ตรงนี้แยกสิ่งที่เจอเป็นสองชนิด

**หยุด (block)** — ผลลัพธ์เชื่อไม่ได้ เช่นจำนวนแถวเปลี่ยน, ไฟล์บนดิสก์ไม่ตรงกับที่คำนวณ,
`device_id` ซ้ำ, ตาราง `prepared/` เก่ากว่า `Raw Data`

**ให้คนดู (review)** — เจอของใหม่ที่กติกายังไม่รู้จัก เช่นหน่วยแบบใหม่, ค่าหลุดช่วงฟิสิกส์,
เลขค้างในช่อง description, เปเปอร์ที่เขียน DOI สองแบบ → **pipeline เดินต่อ** ค่านั้นเป็นว่าง
หรือถูกติดธงที่แถว แล้วรวมเป็น `processed/review/review_queue.csv`

ค่าที่ตีความไม่ได้จะ **ไม่ถูกเดาแทน** — เป็นว่างพร้อมบันทึกเหตุผลใน `*_note`
`--strict` ดัน review ขึ้นเป็น block ทั้งหมด (ได้พฤติกรรมเดิมกลับมา)

## เพิ่มเคสใหม่โดยไม่แก้โค้ด

การแก้รายเครื่องทั้งหมดอยู่ใน `pipeline/overrides/*.csv` เพิ่มเคส = เพิ่มบรรทัด

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `param_fix.csv` | ค่า parameter ที่กรอกผิด (ยืนยันจาก SI) |
| `desc_recover.csv` | ค่าที่ผู้กรอกใส่ในช่อง Descriptions แทน Parameter |
| `prop_value_fix.csv` · `prop_fix_bandgap.csv` · `sign_fix.csv` | ค่า property ที่แก้ตามต้นฉบับ |
| `prop_add.csv` | ค่าที่เปเปอร์รายงานแต่ไม่ได้กรอกลงไฟล์ |
| `stab_temp_fix.csv` | อุณหภูมิเงื่อนไขเสถียรภาพที่ไม่ได้กรอก |
| `material_amount_fix.csv` | ปริมาณสารตั้งต้นที่เป็น typo ในเปเปอร์ |
| `base_alias_recheck.csv` | ชื่อย่อที่ต้องยุบเข้ากับชื่อเต็ม |
| `phys_range.csv` | ช่วงค่าที่เป็นไปได้ทางฟิสิกส์รายปริมาณ |
| `pce_mismatch_known.csv` | เครื่องที่ pce ≠ voc·jsc·ff/100 แต่ตรวจแล้วอธิบายได้ |
| `retention_x100_confirmed.csv` | retention ที่ยืนยันแล้วว่าต้องคูณ 100 (พร้อมข้อความ note ของแต่ละเคส) |
| `pending_papers.csv` | เปเปอร์ที่รอเปิด -- พิมพ์ท้ายทุกครั้งที่รัน เพื่อไม่ให้เรื่องค้างหล่นหาย |
| `known_deviations.csv` | ไฟล์ผลลัพธ์ที่ตั้งใจให้ต่างจาก notebook พร้อมเหตุผล (ดูหัวข้อถัดไป) |

override ที่จับไม่เจอแถวแล้ว (device ถูกถอดออก) จะ **ข้ามให้** พร้อมขึ้น review
ถ้าจับได้เกิน 1 แถวถือว่ากำกวม → หยุด เพราะอาจเขียนผิดตัว

## ⚠ จุดที่ห้ามแก้เล่น

- ข้อความใน `*_note` ทุกอันถูกเขียนลง CSV จริง แก้ข้อความ = ไฟล์ผลลัพธ์เปลี่ยน แล้ว verify ไม่ผ่าน
- `parsers.is_num_re` กับ `is_num_float` ให้ผลต่างกัน และถูกเรียกคนละจุดตาม notebook เดิม
  (notebook นิยาม `is_num` ซ้ำกลางทาง) สลับกันแล้วผลเพี้ยนแบบไม่มีสัญญาณ
- ลำดับการเพิ่มคอลัมน์ในขั้น 2 กำหนดลำดับคอลัมน์ใน CSV — สลับบรรทัดแล้ว verify ไม่ผ่าน
